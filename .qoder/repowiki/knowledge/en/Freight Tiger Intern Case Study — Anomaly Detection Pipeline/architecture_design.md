The root holds no executable entry point; it is a data-and-spec bundle consumed by the `freight_watchdog` child. The pipeline's data contract is defined by four top-level CSVs: `shipment_records.csv` (raw weekly shipments over ~10 months across six origin-destination corridors), `context_notes.csv` (RAG knowledge base of disruptions/events keyed by `applies_to` and date), `sample_output_format_v2.csv` (the canonical row schema the pipeline must emit), and `FreightTiger_Intern_CaseStudy.pdf` (the problem statement). The child code reads `shipment_records.csv`, aggregates per-route weekly `cost_per_tonne_km`, compares against own-history and similar-length peers, retrieves matching notes from `context_notes.csv` via RAG, applies strict rules to produce `flagged`/`matched_note_id`/`reason`, and writes rows conforming to the header in `sample_output_format_v2.csv`. There is no runtime wiring at the parent level — the parent is purely the dataset + spec boundary.
